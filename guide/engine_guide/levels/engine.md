# The engine crates: what lives in `modules/engine`

## Summary

`modules/engine` holds the engine itself in five crates. Two of them are shared DLLs that every module uses: `pill_core`, the foundation, and `pill_engine_core`, the ECS and everything built on it. A third, `pill_engine`, is the crate every module uses to reach the engine, and it is compiled into each module separately. The last two only generate code at compile time.

## At a glance

| Crate                | Built as              | Size        | What it is                                                                        |
| -------------------- | --------------------- | ----------- | --------------------------------------------------------------------------------- |
| `pill_core`          | DLL (and `rlib`)      | ~8k lines   | The foundation every Pill crate links: errors, logging, profiling, platform layer |
| `pill_engine_core`   | DLL (and `rlib`)      | ~54k lines  | The engine: ECS, scheduler, assets, scenes, persistence, the module contract      |
| `pill_engine`        | `rlib`, one per module| ~1.5k lines | What projects and extensions use: re-exports the core, holds the module's registries |
| `pill_core_macros`   | procedural macro      | ~0.8k lines | `#[engine_error]`                                                                 |
| `pill_engine_macros` | procedural macro      | ~5k lines   | `PillComponent`, `#[pill_module]`, the C# mirror attributes and more              |

```
          project, extensions, editor shell
                       │  use pill_engine::*
                       ▼
   pill_engine                one copy compiled into every module's DLL:
                              re-exports the core and holds this module's registries
                       │
                       ▼
   pill_engine_core.dll/.so   one copy per process:              ◄── code generated by
                              the ECS and everything on it            pill_engine_macros
                       │
                       ▼
   pill_core.dll/.so          one copy per process:              ◄── code generated by
                              errors, logging, platform, Rayon pool   pill_core_macros
```

## Why is the engine split into these crates?

The engine is split so that hot reload can replace a module's code while the engine's state stays loaded.

Two things pull in opposite directions:

- **Engine state must exist once.** There must be one world, one asset store, one logger and one thread pool, no matter how many modules are loaded. If every module had its own copy, a reloaded module would start talking to a fresh, empty engine. So that code lives in DLLs that the host loads once and keeps for the whole run.
- **Each module's declarations must stay separate.** The engine needs to know which components, ECS systems and hot-patchable functions *this* module declared, so a reload can tell what the new version added or dropped. So the lists holding them are compiled into each module separately.

The crates follow that line: `pill_core` and `pill_engine_core` are the shared, one-per-process part. `pill_engine` is the per-module part. The macro crates are separate only because Rust requires procedural macros to live in their own crates.

> **Example:** you edit `pill_physics` and save. The host unloads the old physics DLL and loads a new one. The world in `pill_engine_core.dll/.so` keeps every entity, and the logger in `pill_core.dll/.so` keeps writing to the same output. The new physics DLL brings its own fresh copy of `pill_engine`, whose registries list exactly what the new physics code declares.

How these DLLs are linked in development and shipping mode is in [modules_linking_in_pill.md](hosting/modules_linking_in_pill.md).

## What is in `pill_core`?

`pill_core` holds everything that must exist once per process, plus small types every crate needs:

- **Errors** (`error/`): the error types every crate uses. They combine into one `HostError`.
- **Logging** (`telemetry`): the log targets (`telemetry_target::ECS` and the others), the log line formatter, the subscriber setup and metrics.
- **Profiling** (`profiling.rs`): the Tracy `profile_scope!` macros. They compile to nothing when profiling is off.
- **The platform layer** (`platform/`): the clock, log output and futures. This is the only code that differs between native builds and the web, which is why time is measured with `pill_core::platform::Instant` and never `std::time::Instant`.
- **State with one copy per process:** the Rayon thread pool, the native buffer allocator and the change ticks that record when each ECS system last ran.
- **Small shared types:** `FixedString`, `DynamicBuffer`, `SlotMap`, colors and math aliases.

### Why is `pill_core` separate from the engine?

`pill_core` is separate because many crates need logging, errors and the clock but have nothing to do with the ECS.

`pill_renderer_api`, `pill_ui_frame`, `pill_ui_theme`, the player and the development host all link `pill_core`. If it were part of `pill_engine_core`, each of them would pull in the whole ECS just to write a log line.

### Why must `pill_core` be a shared DLL?

`pill_core` must be shared because its state breaks when it is copied.

If each module had its own copy, each module would start its own Rayon thread pool. Those threads would wait inside the module's code. When a hot reload unloads that module, the threads would be left running in unloaded code, and the host would crash. With one shared copy there is one pool, and it never unloads. This is also why a module must never build its own thread pool.

## What is in `pill_engine_core`?

`pill_engine_core` is the engine: an archetype-based ECS and everything built on it.

| Area                         | Files                                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| ECS storage                  | `entity.rs`, `component.rs`, `archetype.rs`, `resource.rs`, `commands.rs`                                               |
| Queries                      | `query/`: filters, iteration, change detection, `Res` and `ResMut`                                                       |
| Running ECS systems          | `system.rs`, `scheduler.rs`, `engine.rs` (the `Engine` type and its update)                                              |
| Field layouts                | `component_field/`: the description of each component's fields that the Inspector, scenes and C# read                  |
| Assets                       | `asset_store.rs`, `asset_database.rs`, `asset_import_registry.rs`, `asset_metadata.rs`, `asset_standalone.rs`, `asset_loading.rs`, `saved_references.rs` |
| Saving, scenes and migration | `persistence/`, `scene.rs`, `startup_scene.rs`                                                                           |
| Settings                     | `settings.rs`, `manager_settings.rs` (settings assets for managers)                                                      |
| The module contract          | `module_abi.rs`, `api.rs`, `hot_patch.rs`                                                                                |
| Other                        | `input.rs`, `debug_draw.rs`, `mirror.rs` (the C# mirror), `scripting.rs`, `diagnostics.rs`                              |

The concept pages explain the main parts: [components.md](../concepts/components.md), [resources.md](../concepts/resources.md), [systems.md](../concepts/systems.md), [entities.md](../concepts/entities.md) and [assets.md](../concepts/assets.md).

### How does a module call into the engine?

A module calls the engine's normal Rust API through a pointer the host gives it.

When the host loads a module, it calls the module's `pill_module_init` and passes an `EngineApi`. That is a small `#[repr(C)]` struct holding a pointer to the host's `Engine`. The module turns the pointer back into `&mut Engine` and then calls the same functions the host uses, such as `world.insert_resource(value)`, `world.get_resource::<T>()` and typed queries.

Both sides of this contract are Rust. A language-neutral contract would need a table with one function pointer per engine operation. Much of the engine's API is generic (`get_resource::<T>`, `Query<&mut T>`), and a table of plain function pointers cannot express generic functions without a second implementation of the whole API.

A module does not register its components, ECS systems or resource types by calling the engine. It declares them where they are defined, and its entry point registers them from the module's registries. `World::register_component::<T>()` is still public, but only tests and hosts that own their own types call it.

The cost is that every module must be compiled against the same engine source and the same features. Development mode does this anyway, because the host builds every module from source at start-up. `EngineApi` is a struct rather than a bare pointer so a field can be added without changing every entry point's signature. Adding a field still means rebuilding every module.

### What must `pill_engine_core` never do?

`pill_engine_core` follows two rules:

1. **It never depends on `pill_engine` and never reads a registry.** Rust links a crate once per DLL. If the core depended on `pill_engine`, the core's own copy of the registries would be shared by every module, and the per-module lists would stop working. When the core needs to know what a module declared, the module passes that in.
2. **It stays free of crates with large import lists,** such as the `windows` crate. Every hot patch generates an import library for each DLL the patch refers to. A core that imported thousands of Windows functions would make every hot patch slower. Import libraries are a Windows linker concept: on Linux a patch links against the `.so` files directly, so this cost only affects Windows builds.

`test_engine_layout.py` checks the first rule. No test checks the second one, so a reviewer has to catch it.

## What is in `pill_engine`?

`pill_engine` is the crate every project and extension uses to reach the engine. It does two jobs:

1. **It re-exports `pill_engine_core` under the same paths.** `use pill_engine::*` gives a module the whole engine. The macros can always write `::pill_engine::...` in the code they generate, whichever crate they run in.
2. **It holds the module's registries.** A registry is a list of what one module declared. `pill_engine` holds them in `component_registry.rs`, `declarations.rs` and `hot_patch.rs`. They are built with the `inventory` crate: `#[derive(PillComponent)]`, `#[system]`, `#[derive(PillResource)]`, `#[derive(PillAsset)]` and `#[pill_hot]` each add an entry at compile time.

### Why is `pill_engine` compiled into every module?

`pill_engine` is an `rlib`, so every module DLL gets its own copy, and with it its own registries.

The registries answer questions about one module: which components this DLL declares, which ECS systems, and where a hot-patchable function lives in this DLL. If they lived in one shared DLL, every module's declarations would land in the same lists. A reloaded physics DLL could then not tell its new declarations from the project's, or from its own previous version's.

The rule that follows: anything collected with `inventory` belongs in `pill_engine`. Everything else belongs in the engine core.

> **Example:** the project declares `PlayerComponent` and `pill_physics` declares `RigidBodyComponent`. The project's copy of `pill_engine` lists only `PlayerComponent`, and the physics DLL's copy lists only `RigidBodyComponent`. When physics reloads, the host reads the new physics list and registers what it finds. The project's list is never touched.

### Who links the engine core without `pill_engine`?

Projects, extensions, the editor shell and hot patches always use `pill_engine`. Some crates link `pill_engine_core` directly instead:

- **Other shared DLLs** (`pill_ui_frame`, `pill_ui_theme`, `pill_project_ui`, `pill_editor_core`). A shared DLL that contained `pill_engine` would break Rust's linking for any executable that links both that DLL and `pill_engine`. These crates also declare nothing that needs a per-module registry.
- **Executables such as `pill_editor`**, which only need the engine's types (for example its input events).

`pill_engine` also has a small executable target (`src/main.rs`). It creates an `Engine` and logs the entity count, so a library that cannot start fails visibly.

## What do the two macro crates generate?

The macro crates generate code at compile time. They never end up in a DLL.

- **`pill_core_macros`** provides `#[engine_error]`. You write an error's message once in `#[message(...)]`, and the macro generates the plain text, the `miette` diagnostic code and the coloured terminal output from it.
- **`pill_engine_macros`** provides:
  - `PillComponent`: the `Component` impl, the field layout and the registry entry;
  - `PillLayout` and `pill_value_type!`: a field layout without registering anything;
  - `#[pill_module]` and `#[pill_project]`: the functions a module's DLL exports (`pill_module_init`, its ABI version), wrapped in a panic guard;
  - the `pill_mirror_*` attributes and `PillMirror`: Rust functions and types that C# code can call.

Everything `pill_engine_macros` generates refers to the engine as `::pill_engine::...`. That is what makes a registration land in the registry of the DLL being compiled, and not in some other module's.

## How do these crates differ between development and shipping mode?

In development mode the two shared crates are DLLs. In shipping mode everything is linked into one executable.

| Crate              | Development mode                         | Shipping mode                      |
| ------------------ | ---------------------------------------- | ---------------------------------- |
| `pill_core`        | `pill_core.dll/.so`, loaded once by the host | linked into the executable         |
| `pill_engine_core` | `pill_engine_core.dll/.so`, loaded once      | linked into the executable         |
| `pill_engine`      | one copy inside each module's DLL        | linked into the executable         |
| Macro crates       | run at compile time only                 | run at compile time only           |

Each shared crate is built as both a `dylib` and an `rlib` so it can be used both ways.

Development mode has one strict requirement. The names of the functions the two shared DLLs export include a hash of the features they were built with. The host and every module must therefore be built with exactly the same features. If one module is built differently, it looks for function names the loaded DLLs do not have, and loading fails with "procedure could not be found" on Windows, or `undefined symbol: …` on Linux.
